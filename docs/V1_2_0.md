# 1.2.0 — Correction-aware learning loop

**Headline:** when the operator corrects the agent's claim in chat, the
system captures the pair, proposes a one-line behavior fix, and queues
it for review. One operator click promotes the candidate into a durable
`behavior_instruction` that lands in every future
`<behavior_instructions>` envelope. The next session reads the rule
before answering and tunes its caution.

## Why

In the 1.1.1 design session the agent made three confident-but-wrong
assertions and was corrected each time. None of the corrections produced
a durable artifact in memory — the lessons died with the chat. v1.10
closes that loop. It makes the README claim *"memory shapes behavior via
operator-trace"* an actual mechanism rather than an explicit operator
chore (`upsert_behavior_instruction` was the only path before).

## Three-stage pipeline

```
1. CAPTURE  (scripts/inject_memory_context.py UserPromptSubmit hook)
   Reads transcript_path JSONL, finds the most recent assistant text
   turn within MEMORY_CORRECTION_PAIR_WINDOW_MIN minutes (default 30).
   If the current user prompt matches the correction heuristic, the
   hook ingests two episodes back-to-back. Each carries BOTH the
   namespaced v1.10 marker (``correction_role``) and the legacy
   ``kind`` field for backward compatibility:
     - claim       (source_type=agent_action,
                    metadata.correction_role="claim",
                    metadata.kind="correction_target")
     - correction  (source_type=user_message,
                    metadata.correction_role="user_correction",
                    metadata.kind="user_correction",
                    metadata.correction_target_episode_id=<claim id>)

2. EXTRACT  (src/agent_memory_lite/extraction/correction_extractor.py)
   Registered in auto_promote._build_extractors alongside
   HeuristicExtractor and the Ollama LLM extractor. On a
   user_correction-tagged episode, the CorrectionExtractor:
     - resolves the paired claim text from the database,
     - distills a one-line rule via correction_distill.distill_rule,
     - emits MemoryCandidate(kind=CORRECTION) with confidence
       0.50 / 0.70 / 0.85 from the regex match (body / opener / both),
     - enforces MEMORY_CORRECTION_MAX_PER_DAY (default 20 per
       workspace per UTC day) before producing the candidate.

3. PROMOTE  (POST /memory/promote_candidate_to_behavior)
   Operator-driven; never auto-fires. Calls
   upsert_behavior_instruction with source_type="memory_candidate",
   source_id=<candidate.id>. The candidate flips to status='promoted'
   with promoted_target_type='behavior_instruction' and
   promoted_target_id=<behavior.id>.

   Optional parameters:
     - pinned: true   — pin the resulting behavior_instruction so it
                        rides every active envelope regardless of
                        query relevance.
     - overwrite: true — replace an existing active behavior_instruction
                         with the same name in this workspace. Without
                         this, a name collision returns 409 to prevent
                         silent rule replacement.
```

## Heuristic patterns

`src/agent_memory_lite/extraction/correction_patterns.py` exposes three
compiled regexes:

* `CORRECTION_OPENERS` — top-of-message contradiction tokens. Bilingual:
  Russian (`нет, ` / `неправильно` / `неверно` / `поправляю` / `я
  буквально` / `я только что`) and English (`no, ` / `wait,` /
  `actually,` / `i literally <verb>` / `that's wrong` / `you're wrong`).
* `CORRECTION_BODY` — mid-message contradiction phrases (`это не так` /
  `ты не прав` / `<subject> не мог` / `that doesn't` / `that's not` /
  `cant`). Apostrophes optional so contracted and uncontracted forms
  both match.
* `LIKELY_AGREEMENT` — negative filter for short messages that *look*
  contradictory but are agreement-with-negation (`нет проблем` / `no
  problem` / `nope`).

The dataclass `CorrectionMatch` records confidence + which patterns
matched, for downstream telemetry and operator-facing explanations.

## Env flags (defaults ON; flag-off path locked by parity test)

```
MEMORY_CORRECTION_DETECT_ENABLED=true        # master gate
MEMORY_CORRECTION_TRANSCRIPT_READ_ENABLED=true  # privacy opt-out
MEMORY_CORRECTION_MIN_USER_LEN=30             # reject very short replies
MEMORY_CORRECTION_MIN_AGENT_LEN=50            # reject empty claims
MEMORY_CORRECTION_MIN_CONFIDENCE=0.5          # threshold for candidate
MEMORY_CORRECTION_MAX_PER_DAY=20              # per-workspace daily cap
MEMORY_CORRECTION_PAIR_WINDOW_MIN=30          # max minutes claim-to-correction
```

`tests/invariants/test_v110_parity.py` enforces flag-off byte equivalence
to v1.1.1.

## How to use it from agent perspective

You don't have to do anything explicit. When the operator corrects you:

1. The hook ingests the pair automatically (no agent code change).
2. The candidate appears in `<pending_review>` of the next
   `memory_get_context` envelope, with `kind="correction_candidate"`
   and a hint pointing at the promote endpoint.
3. The operator reviews, edits the rule text if needed, and clicks
   promote.
4. From the next session onward, the new `behavior_instruction`
   appears in `<behavior_instructions>` of every envelope, with
   `source_type="memory_candidate"` lineage so you can see why the
   rule exists.

## Episode dedup bypass for correction pairs

`MEMORY_EPISODE_DEDUP_ENABLED=true` (default) collapses near-duplicate
episodes into the existing row. This is wrong for correction pairs:
when the user makes the SAME correction twice (same text), the second
pair represents a **recurring mistake** — the strongest signal that a
behavior rule is needed. Collapsing them would silently drop the
second candidate and the operator would never see the recurrence.

The fix in `ingestion/episode_pipeline.py` skips `maybe_dedup` when
`metadata.correction_role` is `"claim"` or `"user_correction"` (or the
legacy `metadata.kind` carries `"correction_target"` /
`"user_correction"`). Each correction pair is treated as a distinct
event. Lock test: `tests/integration/test_correction_loop_e2e.py::
test_correction_pair_bypasses_episode_dedup`.

## Trust gate stays intact

CORRECTION-kind candidates pass the trust gate (they're non-procedural)
and meet the lowered `(0.5, 0.5)` threshold. But the gate forbids
auto-promotion to behavior_instructions; the only path is the explicit
`/memory/promote_candidate_to_behavior` route, which requires operator
input on `name` + (optional) `rule_text_override` + the four enum fields
(`kind`, `scope`, `priority`, `conflict_policy`).

## Validation

* **Retrospective verification:** `tests/integration/test_correction_detector_on_corpus.py`
  catches all three documented corrections from the v1.10 design
  session at confidence ≥ 0.5.
* **Flag-off parity:** `tests/invariants/test_v110_parity.py`
  confirms behavior matches v1.1.1 when the master flag is off.
* **End-to-end:** `tests/integration/test_correction_loop_e2e.py`
  walks the full pipeline (claim ingest → correction ingest →
  candidate emit → envelope visibility → promote → behavior_instruction
  visibility in next envelope).
* **Crash-test phase 26:** `scripts/crash_test/phases/p26_v110_correction.py`
  runs the same loop against the QA workspace.

## Operator review queue

```bash
curl -X POST http://127.0.0.1:8765/memory/list_candidates \
  -H "Content-Type: application/json" \
  -d '{"workspace_id":"<ws>","statuses":["new"],"limit":20}'
```

Filter the response for `kind == "correction"` to see pending correction
candidates. The `<pending_review>` envelope block also exposes them at
the top of every `/memory/get_context` response.

## Audit-log additions

* `write_memory_candidate` (existing action; produced by
  `auto_promote.write_memory_candidate` for every new candidate
  including CORRECTION).
* `memory_candidate.promoted_to_behavior` — operator promoted via
  the new endpoint.

Throttle rejections (`extraction.correction_rejected_throttled`) are
emitted to the application log only — the audit table is not bumped
to keep its growth rate flat.
