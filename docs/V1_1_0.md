# agent-memory-lite 1.1.0 — operator guide

Three follow-on improvements to the v1.4-v1.9 evolution loops, calibrated
on real copyBot data (see `docs/V1_1_0_CALIBRATION.md`).

**Default state changed (post-A+ calibration).** Every v1.4–v1.9 + v2 flag
now ships **ON** so a fresh checkout opts into the loops out of the box.
To restore the v1.0.x baseline, set the corresponding env var to `false`
(or `0.0` for `MEMORY_SENTINEL_AUTORUN_HOURS`). The
`tests/invariants/test_v2_parity.py` invariant locks the flag-off path.

This file is the operator-facing answer to "what are these flags, what
do I monitor, how do I roll back?"

## What v2 closes that v1.4-v1.9 left open

| Gap from v1.4-v1.9 plan                                          | v2 closes it via         |
|------------------------------------------------------------------|--------------------------|
| `memory_usage_feedback` only fills if the agent calls `record_usage_feedback` (it almost never does → EWMA term stays near zero) | implicit_feedback (v2.1) |
| Pending decision/insight candidates only visible via separate `/memory/list_candidates` call — agents forget to check | `<pending_review>` envelope block (v2.2) |
| Sentinel runs depend on a 24h cron — drift can sit invisible for a day | sentinel scheduler on traffic (v2.3) |

## v2.1 — implicit feedback

**Module:** `src/agent_memory_lite/maintenance/implicit_feedback.py`
**Flag:** `MEMORY_IMPLICIT_FEEDBACK_ENABLED` (default `true` post-calibration)
**Audit reasons:** existing `record_usage_feedback` audit rows tagged
`source=implicit_archive | implicit_promote | implicit_link`

Operator actions already encode "useful / noise" judgement. Pre-v2 they
stayed in `audit_log` only. v2.1 maps them to `memory_usage_feedback`
rows so the v1.4 EWMA aggregator picks them up:

| Operator action               | Implicit feedback row             |
|-------------------------------|-----------------------------------|
| `archive(chunk \| decision \| theory \| ...)` | usefulness `-1.0`, source `implicit_archive` |
| `promote_candidate` (any target)              | usefulness `+0.7`, source `implicit_promote` |
| `link_capability(target, strength=W)`         | usefulness `W`,    source `implicit_link`   |

Wired call sites: `api/routes/archive.py`, `api/routes/candidates.py`
(promote path), `api/routes/capability_links.py`. The mapping table is
local to `implicit_feedback.py` so unsupported source/target types
return `False` silently rather than blocking the operator action.

**When to enable:** as soon as you have ≥10 archives or ≥10 capability
links recorded for the workspace. Below that, EWMA has too little signal.

**What to monitor:**

* `/memory/feedback_summary` — total rows, breakdown by `source`. Watch
  the `implicit_*` shares grow.
* `/health.feedback_self_loop_ratio` — should stay near 0. A sudden
  jump means the agent is recording feedback on its own outputs.

**Tests:** 8 unit tests in `tests/unit/maintenance/test_implicit_feedback.py`
(flag gating, source-type whitelist, strength clamp, unsupported types).

## v2.2 — pending review envelope

**Module:** `src/agent_memory_lite/retrieval/pending_review.py`
**No flag** — purely data-driven. The block injects only when the
workspace has at least one `decision_candidates` or `insight_candidates`
row in `pending` status.

Pre-v2: a candidate could sit in the queue indefinitely because no
`get_context` call surfaced it. Agents had to remember to call
`/memory/list_candidates` separately.

Post-v2: the envelope returned by `/memory/get_context` contains a new
section just before `</memory_context>`:

```xml
<pending_review>
  <decision_candidates total="3">
    <ref id="dc_..." title="..." theory_id="th_..." created_at="..."/>
    ...
  </decision_candidates>
  <insight_candidates total="0"/>
</pending_review>
```

Up to 5 items per kind are listed in full; the `total` attribute
signals when more exist. Agents read this and, if appropriate, call
`/memory/promote_decision_candidate` or `/memory/promote_insight_candidate`
without an extra discovery round-trip.

**When to enable:** automatically active in v1.7 / v1.8 (those features
are the source of these candidates). If v1.7 / v1.8 are off, the section
stays empty and is suppressed.

**What to monitor:**

* `/health.pending_review.total` — long-running positive value means
  candidates are accumulating without being reviewed.

**Tests:** 7 unit tests in `tests/unit/retrieval/test_pending_review.py`
(empty/populated load, XML escaping, per-kind cap of 5).

## v2.3 — sentinel scheduler on traffic

**Module:** `src/agent_memory_lite/maintenance/sentinel_scheduler.py`
**Flag:** `MEMORY_SENTINEL_AUTORUN_HOURS` (default `6.0` post-calibration; `0.0` disables)
**Hub-mode:** in hub mode the scheduler fires for any registered
workspace, using the request-scoped DB path resolved from the
connection (PRAGMA database_list) — not the singleton `settings.db_path`
**Audit reasons:** `sentinel.run_recorded` (existing v1.9 action)

Pre-v2: sentinel runs were either manual (`scripts/memory_watchdog.py`)
or via OS cron. Drift visible only every N hours.

Post-v2: every `get_context` call against the workspace's own
`workspace_id` triggers `maybe_run_sentinels`. If
`workspace_meta.last_sentinel_run_at` is older than
`MEMORY_SENTINEL_AUTORUN_HOURS`, a daemon thread runs sentinels
in the background and stamps `last_sentinel_run_at`.

* Workspace isolation preserved: only fires on
  `request_workspace_id == settings.workspace_id` reads.
* Daemon thread (no blocking).
* Stamp-after-success semantics — failed runs do not advance the timer.

**When to enable:** after you have a sentinel YAML at
`.agent_memory/retrieval_sentinels.yaml`. Recommended interval: `6.0`
hours for active development workspaces, `24.0` for stable ones.
`0.0001` is reserved for crash-test usage (~0.4 s).

**What to monitor:**

* `workspace_meta.last_sentinel_run_at` — must advance during traffic.
* `retrieval_sentinel_results` — rows accumulate; check the `result`
  column for failures.

**Tests:** 7 unit tests in `tests/unit/maintenance/test_sentinel_scheduler.py`
(overdue detection, malformed timestamp, flag gating, stamp within 6 s).

## End-to-end & invariants

* **Crash phase:** `scripts/crash_test/phases/p25_v2_improvements.py`
  archives a chunk, asserts `implicit_archive` row materialises,
  verifies `/health.pending_review` fields, polls
  `last_sentinel_run_at` within 6 s while pinging `get_context`.
* **Flag-off parity:** `tests/invariants/test_v2_parity.py` locks in
  that all three modules behave as no-ops with their flags off.
* **Calibration evidence:** `reports/v1_1_0_calibration/report.md`
  on a real copyBot snapshot — 158 implicit feedback rows, 95% rank
  churn, low-EWMA cohort drops 26 places, biggest faller -51 positions.

## Rollout — defaults already on

Every flag in this document ships ON in `Settings` defaults and in
`.env.example`. A fresh checkout running `python -m agent_memory_lite`
already exercises the loops. No staged rollout is required.

The optional ramp, if you want to introduce flags one at a time on an
existing workspace:

1. Confirm calibration evidence applies to your workspace —
   `python scripts/calibration/replay_implicit_feedback.py --db ... --workspace ...`
   then `ab_compare_decisions.py` to see ranking churn match the
   reference numbers in `docs/V1_1_0_CALIBRATION.md`.
2. If you want to *disable* anything during a transition, set the flag
   explicitly to `false` in your project's `.env` — the explicit value
   overrides the default. Keep it disabled until you've replayed the
   calibration on your data.
3. v2.2 is data-driven — `<pending_review>` only appears when v1.7 or
   v1.8 actually wrote candidate rows. No flag manages it directly.

## Monitoring on a live workspace

* `/memory/feedback_summary` — confirms `implicit_*` rows accumulate at
  expected pace (≥1/day on an active workspace). If implicit_archive count
  stays at 0 over a week, either nothing got archived or the route is
  bypassing `record_implicit_archive`.
* `/health.feedback_self_loop_ratio` — must stay near 0; sudden spikes
  mean the agent is recording usefulness on its own outputs.
* `/health.pending_review.total` — long-running positive value means
  decision/insight candidates are accumulating without operator review.
* `workspace_meta.last_sentinel_run_at` — must advance during traffic
  (within the configured `MEMORY_SENTINEL_AUTORUN_HOURS`). If it sits
  still while traffic flows, check the daemon thread isn't stuck via
  the per-workspace lock (use `sentinel_lock.reset_for_tests()` only in
  unit tests; production lock release happens automatically when the
  daemon thread exits).
* `retrieval_sentinel_results` — rows accumulate over time; failing
  cases reported via `/memory/sentinel_trends`.

## Upgrading an existing v1.0.x workspace

A workspace with a v1.0.x DB (last migration 0019) needs migrations
0020–0025 applied before the new code can read its rows. The service
runs `apply_migrations` automatically on every connection open
(`db/migrations.py:apply_migrations`), so the upgrade is **automatic
on first boot** — no manual step required. Verify after restart:

```bash
sqlite3 .agent_memory/memory.db "SELECT version FROM schema_migrations ORDER BY version DESC LIMIT 1;"
# expected: 0025_hygiene_recurrence
```

Existing rows get neutral defaults (`feedback_ewma=0.0`,
`last_retrieved_at=NULL`, `usage_count=0`, etc.) so retrieval ranking
stays unchanged until the new write paths populate them. EWMA values
become meaningful after the first feedback writes; cold-tracking
becomes meaningful after the first retrieval; capability maturity
after the first `mark_used=true` query.

If you need to roll back the code without rolling back the DB, simply
checkout the older commit. The new columns are backwards-compatible
(`NOT NULL DEFAULT ...` or nullable) so older code ignores them.

## Rollback

Set the corresponding env var to `false` (or `0.0` for
`MEMORY_SENTINEL_AUTORUN_HOURS`). Effect is immediate on next request;
no migration needed. EWMA / cold-tracking columns stay populated but
unused — no data loss. The `tests/invariants/test_v2_parity.py`
invariant guarantees the flag-off path remains byte-equivalent to v1.0.x.
