Основание и границы оценки
Оценка основана на предоставленном описании проекта agent-memory-lite. Live-аудит репозито-
рия, запуск тестов, проверка исходников, проверка фактических результатов команд и нагрузоч-
ное тестирование не выполнялись. Поэтому выводы относятся к архитектуре, заявленной функци-
ональности, полноте операционного контура и рискам, которые видны по описанию.
Проект описан как локальный persistent-memory сервис для AI-агентов. В основе: SQLite как
source of truth, SQLite FTS для точного поиска, LanceDB для векторного поиска, HTTP API, MCP tools,
structured memory objects, audit/hygiene/watchdog/backup/eval tooling.
Ключевой вывод: это уже не простой лог диалогов, а typed working memory system для долговре-
менных агентных рабочих процессов.

3. Что сделано хорошо
3.1. Правильная продуктовая идея
Проект решает не только задачу “найти старую запись”, а задачу “сделать агента устойчиво ум-
нее в рамках проекта”. В описании явно разделены две функции памяти: находить факты поз-
же и влиять на будущую работу через decisions, theories, experiments, skills, playbooks и behavior
instructions.
Обычная ошибка memory-систем - складывать все в один transcript log. Здесь этого нет: память
разделена на episode/chunk слой и typed-memory слой.
3.2. Гибридный retrieval
FTS используется для точных идентификаторов, путей, error strings, ID и конкретных токенов.
Vector retrieval используется для смысловых запросов и парафразов. Это правильное разделение:
FTS надежнее для exact lookup, vector retrieval полезнее для запросов вроде “почему бот завис?”
при chunk text вроде “event loop stall” или “heap pressure”.
Хорошо, что проект не пытается заменить все векторным поиском.
3.3. memory_get_context как основной продуктовый интерфейс
Главная ценность memory-системы не в /memory/search, а в том, что агент получает структуриро-
ванный контекст перед работой. В описании указан XML-like envelope с секциями:

3.4. Candidate-first extraction
Память не должна автоматически превращать любой текст в активное правило или решение.
В проекте ingestion может создавать memory_candidates, но candidates должны проходить
promote/reject. Это снижает риск memory poisoning и накопления ложных решений.
3.5. Хорошая operational maturity
В пакете перечислены audit, hygiene, watchdog, trust dashboard, MCP smoke, backup/restore check,
CI gate, candidate triage, contract check. Это не просто API-проект, а система с обслуживанием, про-
верками и деградационными сценариями.
4. Главные риски
4.1. Retrieval parity не равен retrieval quality
Проверка chunks == chunks_fts == vectors доказывает только полноту индексации. Она не
доказывает, что правильный chunk попадет в top-3/top-10, что memory_get_context не вырежет
важный объект token budget-ом, и что RRF не завысит мусорные кандидаты.
Нужна отдельная retrieval quality suite.
4.2. memory_get_context может быть непрозрачным
Если агент получил плохой контекст, нужно понимать:
• какие кандидаты пришли из FTS;
• какие кандидаты пришли из vector retrieval;
• какие кандидаты пришли из graph/fact retrieval;
• какие были отброшены;
• почему конкретный decision/theory/chunk попал в итоговый envelope;
• сколько токенов заняла каждая секция;
• какие объекты были clipped из-за token budget.
Без explainability отладка retrieval будет медленной.
4.3. Behavior instructions - опасная зона
Behavior instructions имеют высокий эффект на будущую работу агента. Если туда попадет ложное,
устаревшее или malicious правило, система начнет стабильно воспроизводить ошибочное поведе-
ние.
Нужны:
6

===== PAGE 7 =====
• priority model;
• conflict resolution;
• source tracking;
• expiry/decay;
• review workflow;
• запрет auto-promotion behavior rules из raw episodes;
• явное правило: current user/system/developer instructions override memory.
4.4. Нужна защита от memory poisoning
Пользовательский файл, episode или external content могут содержать фразы вида “сохрани это
как правило”, “игнорируй предыдущие инструкции”, “всегда отвечай так”. Если extraction pipeline
не различает observed content и authorized instruction, память можно отравить.
4.5. Нет достаточных данных о безопасности
В описании есть redaction и localhost HTTP API, но не видно полноценного security model:
• API token;
• encryption at rest;
• access logging;
• retention policy;
• sensitive object classification;
• export/delete;
• redaction test suite;
• isolation между проектами;
• запрет чтения чужих workspace;
• защита MCP config от stale DB path.
4.6. Embedding/versioning может стать проблемой
Если поменять embedding model, dimension, chunking strategy или text normalization, старые vector
rows могут стать несовместимыми с новыми. В описании есть embedding_id, parity и reindex script,
но нужно явно хранить embedding metadata и stale-vector detection.
4.7. Подозрительный timestamp
В загруженном документе указано Generated: 2026-04-30 , при дате подготовки оценки 2026-
04-29. Это может быть рассинхрон timezone, clock drift или будущая дата в generated artifact. Для
memory/audit-системы корректность времени важна, потому что stale candidates, maintenance
events, snapshots и experiments зависят от timestamp-ов.

21. Финальная оценка
Проект уже имеет сильную архитектурную базу. Его главная ценность - не в SQLite/FTS/vector как
отдельных технологиях, а в том, что память представлена как рабочая typed-система: decisions,
theories, experiments, insights, skills, playbooks, behavior instructions, candidates и maintenance events.
Это делает проект полезным для долгоживущих AI-agent workflows.
Главное, что нужно усилить: доказуемое качество retrieval, explainability, governance поведения,
безопасность и versioning векторного слоя. После реализации P0-блока проект можно оценивать
ближе к 9 / 10 для локального agent-memory продукта.
